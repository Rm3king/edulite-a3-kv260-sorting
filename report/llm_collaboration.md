# 大模型协作记录

本文件记录本项目与大模型智能体协作开发的方式、提示词、模型回答、自我纠错轨迹和技能包的提炼过程。技术文档附录 A 为其摘要。

## 1. 智能体工作流

| 角色 | 工具 | 负责 |
|---|---|---|
| 开发者 | — | 目标、规则、所有物理动作（上电、托住、确认）、最终取舍 |
| 应用集成与优化 | Claude Code（AI PC 本机） | 读写工程、运行测试、经 SSH 只读查询 KV260、分析运行日志与逻辑分析仪数据、修复缺陷、写文档与视频脚本 |
| 控制开发与交叉审查 | Codex + AMD Ross 插件 2026.9.1 | HLS 插补核开发、控制与通信问题排查、离线回归、提交材料审阅；HLS 工作中使用 `hls-synthesizable` 与 `hls-run-flow` |
| 交叉评审 | Codex 与 Claude Code | 根据源码、测试和运行记录相互检查，修改后分别进行离线验证与现场复验 |

协作循环：开发者给出目标与边界 → 智能体给出结论并附证据路径（日志、测试、仪器数据）→ 结论与实测不一致时以实测为准 → 把教训写进规则文件或踩坑清单 → 下一轮会话自动遵守。

## 2. 提示词与规则

### 2.1 常驻规则（项目说明文件，每次会话自动载入）

原文摘录：

> 当前正常完整返回本轮承托起点、反馈确认后自动失能已获用户授权，不再每轮重复问。中途悬空、故障保持或不能确认返回时，这个授权不等于自动撤力矩。保留已验证恢复策略；不要增加任何软件异常无条件 reset，不自动 JTAG，不改零点或电机 Flash。

> 答复格式建议：先列证据支持的根因和未证实假设；每条给文件/函数/数据、最小修改、离线验证、物理验收和回退。不要一上来重写控制架构。

规则还包括“不可覆盖的事实”清单，例如：腕部纠偏的实现方式、早期被撤回的结论、手眼外参的精度现状。智能体在写代码和文档时不得与之矛盾。模板见 `skill/llm_hardware_collab/boundary_rules_template.md`。

### 2.2 任务提示词（节选）

| 场景 | 开发者的提示 | 智能体的处理 |
|---|---|---|
| 线上时序证据 | “要不要 CAN 分析仪？用手上的逻辑分析仪怎么测？” | 给出单探针接 CAN-H、2.8 V 阈值、50 MHz 的采集方案；自写解码脚本；统计 15364 个周期 |
| 故障一次改完 | “以后这种问题不允许再出现，一次性改好” | 先定位根因（例如运行目录定位错误），再改代码并补单元测试，最后上机验证 |
| 零重力示教 | “从上位机启动零重力，记录槽位与轨迹，旁边放数字孪生” | 新增示教卡片、孪生视图与测试；首次上机暴露两处问题后修复 |
| 文档 | “先给结论和数据，数字从原始文件来” | 建立事实占位与渲染脚本，文档、指标表、图共用一个数据源 |

## 3. 自我纠错轨迹

| # | 现象 | 智能体的定位过程 | 根因 | 纠正 | 验证 |
|---|---|---|---|---|---|
| 1 | NPU 量化后检测全部漏检 | 逐层比对浮点与 INT8 输出 | 检测头的框坐标（0–1280）与类别分数（0–1）在同一张量里，单一 INT8 尺度把分数压成零 | 解码节点保持浮点，卷积主体留在 NPU | 抓取目标层面 270/274 个三维目标与 GPU 匹配 |
| 2 | 操作员确认“已托住”后机械臂不失能 | 对比标记文件路径与当前拥有者进程的运行目录 | 确认标记写进了上一次运行的目录 | 按当前拥有者进程定位运行目录 | 新增单元测试；上机复验 |
| 3 | 关闭检测预览窗口后检测程序退出 | 读进程退出日志 | OpenCV 窗口句柄失效抛异常 | 窗口丢失后无界面继续运行；相机自愈 | 关闭窗口后检测持续输出 |
| 4 | 零重力首次启动无响应 | 读电机运行模式寄存器 | 机械臂断电重启后运行模式复位为 0 | 启动前写位置模式基线 | 之后的零重力启动直接进入拖动 |
| 5 | “结束零重力”后 PL 残留故障 | 读板端日志的结束序列 | 终止信号打断了清理流程 | 改为写控制标记，由板端完成结束序列 | 结束后控制与故障寄存器为 0 |
| 6 | 数字孪生滞后 | 测轮询间隔与链路延迟 | 两者叠加 | 轮询 100 → 50 ms，按实测速度外推约 90 ms | 孪生与实物同步 |
| 7 | 5 ms 周期偶发晚点约 1 ms | 逻辑分析仪逐周期统计，按总线事务分类 | 晚点超过 250 µs 的 548 个周期全部与位置读取事务同时出现 | 写入失败分析与改进方向；周期锚定绝对栅格，晚点不累积 | 线上统计与 PL 发送计时监视器互相印证 |
| 8 | 按模式停止进程误伤自身会话 | 回看命令匹配范围 | `pkill -f` 匹配到了自身与其他服务 | 规则改为只按 PID 停止，查进程用 `pgrep -f "[x]yz"` | 此后未再出现 |
| 9 | 早期“末端减振”百分比结论 | 外部测量无法复现 | 初版结论依据不足 | 主动撤回，改为分别报告关节跟踪 RMSE 与末端振铃基线 | 文档与规则同步更新 |

## 4. 技能包的提炼过程

## 5. AMD Ross 使用记录

- 安装：`amd-ross-agentic-ai-assistant` 2026.9.1，以 Codex 插件形式安装，安装记录含源码提交号。
- 使用：`hls-synthesizable` 在编码阶段检查可综合子集（无动态内存、递归、虚函数、系统调用、不支持的指针转换）；`hls-run-flow` 执行 C 仿真 → C 综合 → C/RTL 联合仿真。
- 结果：C 仿真 7009 项检查通过，最大位置误差 2.98e-8 rad；100 MHz、延迟 3 周期、II=1；联合仿真 1003 次顶层事务通过。
- Vivado MCP 服务端需 AMD 账号下载，本项目未接入；配置步骤写在技术文档附录 C。

### 改进建议

结合本项目的开发过程，建议进一步完善以下能力：

1. **验证结果与工程版本绑定**：本工程包含四个 HLS 模块，默认选择首个配置文件容易混淆目标。建议明确模块选择，将源码、配置及工具版本与验证结果绑定，并识别过期报告。
2. **提供 Kria 板端集成模板**：HLS 核上板还涉及版本兼容、DMA 和缓存维护。建议提供从 AXI 接口到 Linux 驱动的参考模板，包含 ABI 与能力检查、DMA 数据传输，以及非法写入拒绝计数。
3. **补充无 JTAG 的调试路径**：本项目主要通过以太网部署，依靠 PL 监测寄存器和逻辑分析仪定位问题。建议提供寄存器式监测模块及远程读取脚本，便于查看执行周期、超时和拒绝计数。
4. **将仿真向量延伸到板端验证**：我们用真实腕部图像对照 PL 与 ARM 的掩码输出。建议在仿真阶段导出输入和参考结果，配套板端回放脚本，对掩码等确定性输出逐位比较。

安装阶段还可增加统一检查入口，显示技能、命令行工具、MCP 服务及授权是否就绪。
