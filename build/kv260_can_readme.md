# KV260 PL CAN 控制工程

第一版工程服务于 A3 大螺丝分拣项目。PS 经 AXI-Lite 配置，PL 自主按本地时间取发送队列、驱动经典 CAN 控制器、收集反馈。不是 PS CAN 外设经 EMIO 引出，也不是 GPIO 软件模拟 CAN。

当前验收以 `result/latest_validation.json`、完整构建 `result/metrics.json` 和板端回执为准。源码存在或 bitstream 生成不代表外部 CAN／机械臂已经通过。

## 已实现的硬件

- 复用 OpenCores 经典 CAN 控制器，固定版本及修改见 `../../third_party/opencores_can/manifest.json`；保留 LGPL 和原版权头。不是本项目自研 CAN 位级协议核。
- 自研 AXI-Lite 接口，AW/W 独立握手、读写响应保持、对齐／访问检查。
- 16 帧发送队列：29 位 ID、0～8 字节、执行时间和有效期；PL 自动填写 CAN 寄存器并发起发送。
- 16 帧接收队列、微秒时间戳、七电机 Type2 最新反馈表、接收溢出计数。
- 100 ms 默认主机心跳期限；超时关闭外部 TX、复位控制器并清队列，需要重新配置。
- v2：已提交帧到期中止；外部Type1运动帧的逐轴许可、位置/速度/力矩/Kp/Kd编码检查；Type2反馈新鲜度/故障监测。默认禁止所有轴的Type1/Type3发送。
- 内部回环模式：核心 TX 接回核心 RX，外部 TX 强制高；支持不接 USB-CAN 的板上内部链路验收。
- PS/AXI/复位/ILA 完整 Vivado 工程，J2-1/H12 TX，J2-3/E10 RX。

本轮用户确认按 J2-1/3/9/11 完成接线，接受其确认推进；不是 Agent 重新检查了照片或实际电压。依据与编号区别见 [接线计划](../../docs/kv260_a3_control_plan.md)。

## 复现

```bash
/usr/bin/python3 contest/kv260_can/run_tests.py
/usr/bin/python3 contest/kv260_can/software/test_protocol.py
./scripts/create_project.sh bitstream can
/usr/bin/python3 scripts/package_can.py
bash scripts/deploy_can.sh
```

已安装[项目免密管理](../../docs/kv260_project_access.md)时，最后一项直接执行；尚未安装时才需要用户在自己的终端输入 **KV260 的 ubuntu sudo 密码**。部署脚本先校验全部文件，调用 xmutil 卸载旧应用并加载新应用及匹配设备树，运行状态检查和内部回环，最后保持 TX 禁止。没有 JTAG 下载、QSPI/SD 刷写、自动使能机械臂、设置零位或永久参数写入。

板端常用入口（部署后 `~/kv260_can_deploy/`）：

```bash
gcc -O2 -Wall -Wextra -Werror -shared -fPIC mmio.c -o libkv260_mmio.so
/usr/bin/python3 canctl.py status
/usr/bin/python3 canctl.py selftest
/usr/bin/python3 canctl.py listen --seconds 10
/usr/bin/python3 canctl.py read-position --motor 1
/usr/bin/python3 read_arm.py --rounds 3
/usr/bin/python3 board_guard_validate.py
```

`selftest` 不驱动外部总线。`listen` 不 ACK、不发错误标志。`read-position` 会发一条 Type17 参数读取并允许 ACK，必须在实际总线接线和电气确认后使用；它不使能电机、不写参数、不发运动指令。没有主动上报时，被动监听无数据不是故障结论。

`a3_protocol.py` 提供纯编码／解码函数，实际 SDK 离线比对时剥离 SocketCAN 的 bit31 EFF 元数据后比较 29 位 ID。它的范围是电机协议范围，不是实际机械臂关节限位；不能直接把关节坐标当电机坐标发送。

## 寄存器摘要

UIO 名称 `kv260-can`，物理地址 `0xA0000000`，长度 4 KiB；仅打开匹配名称并校验签名。

| 偏移 | 含义 |
|---|---|
| 0x000～0x0FC | CAN 字节寄存器按 32 位字对齐，原寄存器 N 对应 N×4；调度使能时禁止软件写原始寄存器 |
| 0x400 | 签名 0x43414E31 |
| 0x404 | bit0 外发允许；bit1 PL发送调度；bit2 自动收帧；bit3 内部回环且外部TX禁止；写0复位CAN并清队列 |
| 0x408 | 32 位微秒时间，约71.6分钟回绕 |
| 0x40C | 最近轮询的控制器状态，bit16 IRQ有效，bit17 bus-off |
| 0x410 / 0x414 | 写心跳／读心跳年龄；心跳期限微秒（默认100000） |
| 0x418 | fault：1心跳过期，2总线关闭，4在途帧到期，8运动反馈过期/故障；仅外发禁止时可清除 |
| 0x41C | 高16位RX队列数量，低16位TX队列数量 |
| 0x420～0x42C | 已提交发送数、提交前过期丢弃数、收帧数、RX溢出数 |
| 0x430 / 0x434 | 最近提交CAN命令的本地时间／相对计划时间的延迟 |
| 0x440～0x454 | 暂存due、expiry、ID、DLC、payload高32位、payload低32位 |
| 0x458 | 提交暂存帧入队；满队列／非法格式返回SLVERR |
| 0x460 / 0x464 / 0x468 / 0x46C | 在途中止计数、在途标志、在途expiry、运动守卫拒绝计数 |
| 0x470 | 固件版本0x00030000（v3 PP保护） |
| 0x480～0x490 | RX队首ID、flags、数据高／低字、本地时间；flags bit8扩展帧、bit9 RTR、低4位DLC |
| 0x498 / 0x49C | 写出队；读已见电机位图 |
| 0x500＋(ID−1)×16 | 电机ID及状态字、数据高字、数据低字、时间戳，ID1～7、主机FD |
| 0x5A0 / 0x5A4 / 0x5A8 | 逐轴许可mask、反馈超时us、已接受运动轴mask；前两项仅control=0可写 |
| 0x600＋(ID−1)×16 | 四字：位置/速度/力矩范围（低16下界、高16上界），Kp/Kd上限（低16Kp、高16Kd）；仅control=0可写 |

所有写入要求完整32位WSTRB且地址对齐。发送队列是 FIFO，调用者须按 due 排序；时间比较要求半范围内，板端 API 限制未来1秒。未提供任意乱序优先队列。

100 MHz 目标时钟下 BTR0=0x04、BTR1=0x16，对应1 Mbps、80%采样点。板端实际时钟必须经设备树和后续外部波形／USB-CAN复验；不能仅从目标频率推断实际波特率。

## 验证与尚未满足的控制条件

自检覆盖双节点扩展帧、ACK、多种数据填充模式、独立 Python 串行帧生成与错误CRC拒绝、RX FIFO与反馈表、入队期限、心跳和内部回环外部TX抑制。AXI覆盖AW/W先后顺序、响应背压、请求不丢不重及半笔事务复位。原 Day1 回归另外运行。

以下限制必须在机械臂运动前继续解决，不把当前版本当完整运动控制器：

- **due 是向 CAN 控制器提交命令的时间，不是总线 SOF 时间。** 仲裁和忙总线仍会延迟发送；指标 0x434 也不是机械臂端到端抖动。
- **v2增加在途expiry撤销。** 到期复位控制器并禁止TX，可终止无ACK重试；无法撤回已被电机接收的帧。截断正在发送的帧可能引起CAN错误，完成状态轮询滞后可能导致保守中止；仍需忙总线/仲裁测试，不宣称端到端期限保障。
- **心跳超时只禁止新总线输出，不等同机械臂安全停机。** 电机最后目标、重力支撑及电机 CAN 超时配置需实测并明确停止策略。
- RX时间戳为硬件轮询发现待收帧的时间，尚非精确SOF；七电机最新表不等于同步采样。
- 仲裁冲突、错误被动／bus-off恢复、FIFO满载、主机持续访问下的调度上界和长时间运行还需扩展测试。
- `verilator_attempt2.log` 无错误但有遗留核及宽度告警，不能写“lint clean”。当前两个自研宽度提示分别为多位fault转布尔和取移位结果低8位，语义已审阅；上游宽度／casex等保留待加强验证。
- [七轴三次插补核](../trajectory/README.md)独立验证中，尚未接入此 bitstream；限位检查只覆盖单次输出，尚无速度／加速度和整段碰撞保证。
- SDK关节方向/零偏/限位的纯软件映射已实现并离线验证；真实坐标与夹爪边界、单轴／多轴实物控制、相机标定和完整螺丝分拣闭环未验收。

运动守卫作用于队列Type1/Type3，v3进一步限制Type18为7号夹爪PP白名单。原始CAN寄存器与root重新配置仍为受信任开发接口，不能作为防恶意主机边界。内部回环绕过运动守卫，同时强制外部TX为高。`joint_safety.py`提供坐标/量化边界和离线会话校验，尚未接入网络服务；详细实施分工与限制见[控制方案](../../docs/a3_control_implementation.md)。UIO上的SLVERR可能表现为进程总线异常；上层必须先校验，不能靠捕获Python异常恢复非法MMIO写。

外部互测可用原免驱 USB-CAN，无需专门焊线。有现成端子就接 CANH/CANL 与参考地，复核两端终端；不方便时先完成内部回环和机械臂侧只读通信。总线仅保留一个运动命令来源。

## v3 PP夹爪保护与首次运动工具

`0x680`为PP许可；`684/688`为IEEE754 float位置下/上界；`68C/690/694`为正速度/加速度/电流上限，配置仅control=0可写；`698`只读准备位图。默认许可0、无有效位置区间。

外部Type18只接受ID=0x1200FD07、DLC8、保留字节0，并限制为：run_mode=uint8 1；vel_max(7024)、acc_set(7025)、limit_cur(7018)为正有限值且不超过配置；canTimeout(7028)为uint32 2000～20000；loc_ref(7016)为有限值且在配置区间内，需要新鲜无故障Type2。位置比较使用IEEE754符号排序键，支持负角度，不需要浮点运算核。其他电机Type18和其他参数均拒绝；外部Type26亦由硬件拒绝。

7号Type3还需六项准备位全部完成（模式、速度、加速度、电流、超时、初始位置），并且有新鲜Type2。软件另逐参数Type17读回核对，硬件准备位仅代表合法帧已入队，不等于电机确认。使能后加入反馈超时监控，禁止重配模式/限制，只允许受限位置目标。Type4、control0及故障清准备位；队列内Type4不自动清电机故障。内部模式仍绕过运动守卫且物理TX被抑制。

`gripper_commission.py --probe --output probe.json`仅对7号发送不清故障的停止帧和参数读取。`--move`为现场有人监护的首次实验：从新读位置向行程内部0.05rad、速度0.08rad/s、加速度0.2rad/s²、电流上限0.3A，6000计数的电机超时；先当前位置保持，最多2.5秒跟踪，再停止并核实reset反馈。不会自动提高电流、清故障、回零、写Flash或使能其他轴。此实验采用电机内置PP轨迹，不代表HLS插补核已经接入。

停止CAN不等于物理停机保证，电机超时后的实际行为须独立验收；首次试验保留现场断电手段。完整日志与当前实测状态见`reports/gripper_commissioning_20261016/`。


### 夹爪往返复测

`gripper_commission.py --repeat --output repeat.json`执行3次内侧往返，每程0.05rad、PP速度设定0.04rad/s、电流上限0.3A；起点必须距实测机械端点至少0.01rad，每程最长3.5秒，末尾失能并核对reset。同步记录Type2与顺序读取的MECH_VEL参数，不能将这两者当成同时采样。无自动增大电流/清故障/回零/写Flash。

实测6程均到位，最大终点误差0.001619rad（0.092774°），回起点误差0.000384rad。速度读数仍有高于PP设定的峰值，100～135ms位置差分只估计平均速度；尚不证明瞬时物理速度硬限，未将其归因为已确认的解码错误或机械超速。曲线与报告见[往返证据](../../reports/gripper_repeat_20261016/validation.json)。

`probe_arm_parameters.py`只对1～6号发Type17，读取模式配置、位置、速度、电流限值、通信超时；不发使能或失能。mode配置不等于电机运行状态。本次30/30回复，六轴超时均为0。用户明确臂段无承托，因此未使能其他六轴；后续先补承托并逐轴验证模式/停止策略，不能直接全臂使能。

## v4：七轴独立 PP 准备与受承托机械臂调试

固件版本寄存器为 `0x00040000`。7号原 `0x680..0x698` 布局保持不变；1～6号使用 `0x700 + 0x20*(id-1)` 的独立寄存器组，组内偏移依次为许可0、位置下界4、上界8、速度12、加速度16、电流20、只读准备位24。配置仍仅停机可写。每个轴必须独立准备 mode/速度/加速度/电流/非零通信超时/位置六项，并有新鲜无故障 Type2，才能发使能；某轴的准备位不能授权另一轴。使能后禁止改限值，Type4仅清该轴状态，全局故障清全部活动/准备状态。PP许可开启的轴禁止混入Type1命令。该版本收紧了1～6号使能入口，原Type1流需要另行实现对应模式的准备流程。

`software/arm_commission.py` 必须在臂段已经稳固承托、运动范围清空且操作员在旁的条件下使用。`probe --supported-attended` 会发Type4失能并读取七轴位置；**它不是纯只读工具**。`hold` 逐轴配置/读回并使能，已使能轴继续刷新当前位置；`move` 在上述步骤通过后逐轴做0.01rad内侧动作再返回，其他轴保持。速度设0.02rad/s、加速度0.1rad/s²、电流1～6号0.5A/7号0.3A、通信超时6000计数；无法保持/跟随时中止，不自动增大电流。速度设定不等于已验收的物理硬上界。

脚本结束或可捕获异常均尝试逐个Type4并检查新鲜reset反馈，一个轴的失败不会跳过后续轴；随后停止PL队列并清全部运动许可。进程崩溃/掉电时仍依赖电机非零超时与机械承托，尚无安全认证。不要将此有限时长调试脚本当作长时间悬空保持服务。七轴HLS插补仍未接入，当前使用电机内部PP。构建、实机结果分别见 `reports/arm_commissioning_20261016/`，不得由源码存在推定实测通过。

### ABI 0x60003：可恢复的 CAN 提交拒绝与受限易失调参

| 地址 | 含义 |
